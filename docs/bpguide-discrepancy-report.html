Discrepancy Type Reference

Each test case fires both the legacy PHP API and the adapter API in parallel, then compares HTTP status codes and the full parsed response body. Each output row is tagged with one of the following discrepancy types. Types marked Yes under Counts as failure? cause the test to be reported as FAIL; EXPECTED_DIFF rows are excluded from the failure count and treated as accepted/informational differences.

Type Counts as Failure? What It Means Detection Logic
PASS No HTTP status codes and full response bodies are identical on both sides. No differences found. Emitted when zero diff rows are produced for a test after all comparison checks complete.
HTTP_STATUS_DIFF Yes Legacy and adapter returned different HTTP status codes (e.g., legacy 200 vs. adapter 404). Body comparison is skipped — the status difference is the entire result for that test. Triggered before body parsing when legacyResult.status !== adapterResult.status.
CONTENT_MISMATCH Yes A specific field value differs between legacy and adapter, or the adapter is missing a record that legacy returned. Both sides returned the same HTTP status code but their parsed bodies disagree. ICD-aware recursive comparator (compareItemsList) walks both parsed objects. Any leaf-value difference or unmatched legacy item that is not overridden to EXPECTED_DIFF is reported as this type.
EXPECTED_DIFF No (accepted) The adapter returns more content than legacy, or returns a more precise ICD sub-code / updated name from ODG v1.2. These are intentional differences between the legacy content database and ODG v1.2 — not bugs. Set in three situations: (1) adapter returns a property/element that legacy omits; (2) adapter returns extra array items (e.g., more activitymod entries) not present in legacy; (3) the adapter ICD code is a sub-code variant of the legacy root code (prefix-matched but full code differs).
FORMAT_MISMATCH Yes Legacy responded with one format (XML or JSON) but the adapter responded with the other. Detected via Content-Type header inspection and body sniffing ({ or [ prefix → JSON, otherwise XML). Triggered when detectFormat(legacy) !== detectFormat(adapter) after both HTTP calls succeed with the same status code.
PARSE_ERROR Yes One or both responses could not be parsed as valid XML or JSON. Body comparison is skipped and the parse exception message is recorded in the detail column. Triggered when JSON.parse() or XMLParser.parse() throws an exception for either side's response body.
NETWORK_ERROR Yes The HTTP request to the legacy or adapter host failed at the network level (connection refused, DNS failure, 30-second timeout, etc.). No HTTP status code or response body is available. Triggered when axios.get() itself throws (a thrown exception indicates a network-level failure, distinct from an HTTP error response which always yields a status code).

Item 1 — Legacy Drop-Digit Fallback: 5-digit ICD-9 Procedure Codes  PRODUCT ACCEPTED

9 tests in Symetra-ODGDEMO return HTTP 200 from the legacy API but HTTP 404 from the adapter. All involve 5-digit ICD-9 procedure codes (e.g. 10121, 25111, 63047) or a malformed code (5522.32XA). These codes have no exact match in the ODG v1.2 guidelines index.

Root cause — Legacy drop-digit fallback vs. ODG exact match: The legacy PHP system applied a drop-digit (parent-code fallback) algorithm: when a queried ICD code is not found as an exact match, it progressively strips one trailing digit at a time until it finds a matching record. For example, 10121 would be tried as 10121 → 1012 → 101. The ODG v1.2 API performs an exact-code lookup only and applies no drop-digit fallback.

Product decision — confirmed, no adapter fix: The adapter should not auto-correct or apply a drop-digit fallback for unrecognised codes. Silently normalising a submitted code risks returning guidelines for a different code than the one the caller intended, which could cause clinical confusion. The HTTP 404 response from the adapter for these codes is therefore correct and expected behavior. The affected customer (Symetra) should be advised to submit valid ICD-9 or ICD-10 codes that exist in the ODG v1.2 index.

Item 2 — Legacy Parent-Code Resolution for ICD Sub-codes  PRODUCT ACCEPTED

3 tests in MLC-ODGDEMO show a difference in the returned icdcode and name fields. When a customer queries an ICD-10 sub-code (e.g. F22.0), the legacy system resolves it to the parent code (F22) using the same drop-digit fallback algorithm and returns the name from an older content snapshot. The adapter returns the queried sub-code as-is with the current ODG v1.2 name.

Root cause — Legacy drop-digit parent-code resolution vs. ODG exact match: The legacy PHP system stripped the decimal suffix from codes like F22.0 when no exact match existed and returned guidelines for the parent code F22. Because MLC-ODGDEMO is an Australian customer and these codes (F22.0, F23.9, F41.2) exist in the AU ODG v1.2 index as exact sub-codes, the adapter finds and returns them directly — resulting in a different icdcode and name in the response.

Product decision — confirmed, no adapter fix: The adapter should not resolve a queried ICD sub-code to its parent. Returning a different code than the one submitted could cause clinical confusion. The adapter output (exact sub-code with current v1.2 content name) is correct and expected behavior. This decision is consistent with the same resolution applied to the drop-digit fallback cases above.
