Discrepancy Type Reference

Each test case fires a POST to both the legacy PHP API and the adapter API in parallel, then tags each output row with one of the following discrepancy types. Types marked Yes under Counts as failure? cause the test to be reported as FAIL.

Key distinction: For HTTP 200 responses, onesearch performs schema-only comparison (property names, nesting, and data types) — it does not compare actual result values, because search results legitimately differ between legacy SQL and ODG v1.2 Elasticsearch. Full content comparison is only applied to non-200 (error) responses, where both sides must be byte-for-byte identical.

Type Counts as Failure? Applies to What It Means Detection Logic
PASS No All responses HTTP status codes and response schema are identical on both sides. No differences found. Emitted when zero diff rows are produced for a test after all checks complete.
COUNT_INFO No (informational) 200 responses The number of results for a given search type (e.g. ICD10, CPT) differs between legacy and adapter. Both sides have results; only the count differs. This is expected because: (1) the adapter caps results at ~500 per type, while legacy was unbounded; (2) Elasticsearch and SQL return different result sets for the same query. Only records whose key (code/id) exists on both sides are compared for value equality. Emitted after type-level comparison when legacyItems.length !== adapterItems.length and both sides have at least one result. Does not set failingRows.
HTTP_STATUS_DIFF Yes All responses Legacy and adapter returned different HTTP status codes. Body comparison is skipped — the status difference is the entire result for that test. Triggered before body parsing when legacyResult.status !== adapterResult.status.
RESULT_PRESENCE_DIFF Yes 200 responses One side returned a non-empty result set and the other returned zero results, even though both returned HTTP 200. This is a structural disagreement more serious than a count difference. Triggered when hasResults(legacy) !== hasResults(adapter) after both parse successfully with the same HTTP 200 status.
MISSING_IN_ADAPTER Yes 200 responses (schema) A property path present in the legacy response schema is absent from the adapter response schema. The adapter is returning a structurally incomplete response. Schema comparator finds a path in legacySchema with no corresponding entry in adapterSchema.
EXTRA_IN_ADAPTER Yes 200 responses (schema) A property path present in the adapter response schema is absent from the legacy schema. The adapter is returning fields that legacy never included, which could break customer parsers. Schema comparator finds a path in adapterSchema with no corresponding entry in legacySchema.
TYPE_MISMATCH Yes 200 responses (schema) The same property path has a different data type in legacy vs. adapter (e.g. legacy returns a string, adapter returns a number). The schema is structurally compatible but types diverge. Schema comparator finds the same path in both schemas but legacyType !== adapterType.
TYPE_MISSING_IN_ADAPTER Yes 200 responses Legacy returned at least one result for a search result type (e.g. ICD9, ICD10, CPT) but the adapter returned zero results for that same type. The adapter is entirely missing a result category. Triggered after type-level extraction when adapterItems.length === 0 for a type path that has legacyItems.length > 0.
VALUE_MISMATCH Yes 200 responses A field value differs between a legacy record and its matching adapter record (matched by code/id key). Only records present on both sides are compared; records unique to one side are skipped. ICD9/ICD10 name field differences are suppressed as a known permanent quirk (legacy returns the matched description, adapter returns the canonical code name). Key-join: for each type group, builds a code → item map on each side, then calls compareContent(legacyItem, adapterItem) for keys that exist in both maps.
CONTENT_MISMATCH Yes Non-200 responses The error response body values differ between legacy and adapter. Used only when both sides returned the same non-200 status code (e.g. both 403). The error message, structure, and content must be identical. Triggered on the non-200 path: compareContent(legacyNormalized, adapterNormalized) is called (full recursive value comparison, not schema-only).
FORMAT_MISMATCH Yes All responses Legacy responded with one format (XML or JSON) but the adapter responded with the other. Processing continues after this flag so schema differences are also captured. Triggered when detectFormat(legacy) !== detectFormat(adapter) after both HTTP calls succeed with the same status code.
PARSE_ERROR Yes All responses One or both responses could not be parsed as valid XML or JSON. Body comparison is skipped and the exception message is recorded in the detail column. Triggered when JSON.parse() or XMLParser.parse() throws for either side's response body.
NETWORK_ERROR Yes All responses The HTTP request to the legacy or adapter host failed at the network level (connection refused, DNS failure, 30-second timeout). No HTTP status code or body is available. Triggered when axios.post() itself throws (network-level, not an HTTP error response).

Search Engine Architecture Difference

The legacy PHP One Search and the ODG v1.2 /search API use fundamentally different search technologies. This is the primary driver of all status and count differences observed in this report.

Dimension Legacy PHP One Search ODG v1.2 / Adapter
Search engine SQL database — LIKE / REGEXP pattern matching Elasticsearch — full-text indexing, tokenization, relevance scoring
Matching behavior Exact substring or regex match against stored text. Abbreviations, alternate forms, and partial tokens that do not appear literally in the indexed value return 0 results. Tokenized, stemmed, and relevance-ranked search. Abbreviations (e.g. ACJ, CFL), synonyms, and partial term matches resolve to relevant results.
Result count Unbounded — legacy returned full result sets (e.g. 98,767 ICD10 matches for a broad term). Capped at approximately 500 results per search type per ODG API design.
No-results condition HTTP 404 — returned when the SQL query finds zero rows. HTTP 404 — returned when /search returns an empty result set for all requested types.

Item 1 — Adapter Improvements: Elasticsearch Broader Coverage (17 tests)  PRODUCT ACCEPTED

These 17 tests show the adapter returning HTTP 200 with results where legacy returned HTTP 404 or HTTP 500. In every case the difference is attributable to Elasticsearch's superior full-text search capability. These are not regressions — customers using the adapter receive better search results than the legacy system provided.

Product decision — confirmed, adapter behavior is correct: The Elasticsearch-backed ODG v1.2 search correctly resolves clinical abbreviations (e.g. ACJ for acromioclavicular joint, CFL for calcaneofibular ligament), partial terms, and alternate forms that legacy SQL REGEXP could not match. The adapter returning HTTP 200 for these cases is an improvement in search quality. No adapter code change is needed.

One additional case (Symetra-ODGDEMO-TEST-12) involved a legacy HTTP 500 caused by a CDATA special character ()82) breaking MySQL's REGEXP syntax. The adapter handled this gracefully and returned HTTP 200. This is an improvement in reliability.

Item 2 — Regression: AU ICD10 Country Scope (MLC-ODGDEMO-TEST-33)  PENDING PRODUCT DECISION

This is the only customer-visible regression in the One Search comparison. The legacy SQL search found results for the search term; the ODG v1.2 Elasticsearch index does not return results for the same term when called without a country parameter.

Root cause — AU ICD10 content excluded by default US-only scope: The legacy PHP onesearch table was populated with both US and AU ICD10 codes in a single combined index. When an AU customer searched for an AU-specific ICD10 code or term, legacy SQL found it because AU content was present alongside US content.

The ODG v1.2 /search API scopes its Elasticsearch query by country. When no country parameter is supplied, the API defaults to US-only ICD10 search — AU-specific codes that are not part of the US content set are excluded, and the adapter returns HTTP 404.

MLC-ODGDEMO is an Australian customer. TEST-33's search term resolves to AU ICD10 content that exists in the legacy combined table but falls outside the US-only scope the adapter currently uses.

Note: AU country scope in ODG v1.2 is a superset of US — when country=AU is passed, the search returns both AU-specific and all US ICD10 codes. Defaulting to AU would not exclude any US results.
Test Customer Legacy Status Adapter Status Impact
MLC-ODGDEMO-TEST-33 MLC-ODGDEMO 200 404 AU ICD10 code present in legacy's combined US+AU index; adapter's ODG call scoped to US-only → customer-visible regression for AU customers
Product decision required: Should the adapter always pass country=AU to the ODG v1.2 /search API for ICD10 searches?
  • Option A — Always default to AU (recommended): Pass country=AU on every ICD10 /search call. AU is a superset of US content — no US results are lost, and AU-specific codes become reachable. Resolves the MLC regression without affecting US customers.
  • Option B — Per-customer country routing: Determine the customer's country from companymaster (or a new config field) and pass the appropriate country value. More precise, but requires a schema or configuration change per customer.
  • Option C — Accept the regression: Document as a known gap. AU-specific ICD10 codes will return 404 from the adapter. Only viable if no AU customers are planned for the adapter.

Item 3 — Result Count Cap (~500 per type)  PENDING PRODUCT CONFIRMATION

Every test has a result count difference between legacy and the adapter. The ODG v1.2 /search API caps results at approximately 500 per search type (ICD10, CPT, ICD9, etc.). The legacy system had no cap and could return thousands of rows.

Direction Cause Example
Adapter returns more results than legacy Elasticsearch's broader tokenized matching surfaces results that SQL REGEXP did not find. Legacy result sets were often artificially small because abbreviations and alternate terms were not matched. Symetra-TEST-4: legacy 24 results, adapter 500 (capped).
Adapter returns fewer results than legacy ODG v1.2 caps results at ~500 per type. Legacy had no cap. Symetra-TEST-8: legacy returned 98,767 ICD10 results for a broad term; adapter capped at 500.
Product confirmation required: Confirm that the ~500-results-per-type cap in ODG v1.2 is acceptable for all legacy customers migrating to the adapter. If a specific customer requires a higher result limit, this would need to be raised with the ODG API team as a configuration change. No adapter code change is needed regardless of the decision.
