Customer Usage Logging — Design Decision Questionnaire

Document type: Design decision findings & dev team questionnaire  |  Date: 2026-10-05  |  Author: Saurabh Goyal  |  Status: Pending Decisions

Executive Summary

The legacy PHP API writes a row to the webserviceusage database table on every successful customer call, capturing company code, service code, request URI, caller IP, and customer-supplied client ID. The adapter was initially designed to carry per-company OAuth client credentials in the companymaster table so that ODG API's own telemetry would serve as the usage audit trail — eliminating the need for a separate adapter-level usage log.

A security concern has now been raised: storing OAuth client secrets in a database may violate security policy. If a single shared generic credential (stored in the environment / secrets manager) is used instead, ODG API logs cannot attribute calls per customer, and the adapter must implement its own usage tracking. This document presents the findings from the PHP source analysis, the available design options, and the questions the development team must answer before implementation proceeds.

Design Options

Four credentialing + logging approaches have been identified. Each has different security posture, infrastructure impact, and adapter development effort.

Option Approach Pros Cons / Risks Adapter logging needed? ODG API attribution?
A
Current design		 Per-company OAuth credentials stored in companymaster DB columns
  • ODG API logs show per-company calls
  • No new adapter tables needed
  • Simpler token-cache key (already implemented)
  • Client secrets at rest in DB — breach exposes all customer OAuth credentials
  • May violate security policy for secret storage
 Not required Yes — per company
B Single shared generic credential in .env / deployment secrets
  • No secrets in DB
  • Simpler credential rotation (one place)
  • Lower DB breach impact
  • ODG API logs can't distinguish customers
  • Adapter must add a write path and usage table
  • SQLite must become writable (or separate audit DB)
  • All customers share one rate-limit bucket at ODG API
 Required — new webserviceusage table in adapter DB No — all calls appear as one client
C
Recommended		 Per-company credentials in Azure Key Vault (or secrets manager); companymaster stores only a vault reference key
  • Secrets never touch the DB
  • ODG API logs retain per-company attribution
  • No adapter usage table needed
  • Credential rotation handled outside DB
  • Adds Key Vault dependency and infra cost
  • Token cache logic must resolve vault ref → secret at startup/refresh
  • More complex local dev setup
 Not required Yes — per company
D Per-company credentials (DB or vault) + structured JSON log per call to stdout → Datadog
  • No new DB table
  • Usage queryable from Datadog with filters/dashboards
  • Logs can include richer context than webserviceusage
  • Admin dashboard (PHP) cannot read from Datadog — would need migration
  • Log retention and query cost in Datadog
  • Structured log schema must be agreed and versioned
 Structured log to Datadog (no DB table) Yes — per company
Note on Option C (Recommended): This approach eliminates the primary security risk (secrets in DB) while preserving per-company ODG API attribution, avoiding a new adapter write path, and keeping the token-cache mechanism unchanged. The main trade-off is Key Vault infrastructure setup. If Azure is already the deployment target for the adapter, Key Vault is a natural fit.

Open Questions — Dev Team Questionnaire

Please review each question and record your decision or answer. Unresolved questions are blockers before implementing the chosen design option.

Section 1 Security & Credential Storage

Q1. Is storing per-company OAuth client secrets in the companymaster database (currently SQLite, future Azure SQL) acceptable under current security policy? Or must OAuth client secrets be stored in a secrets manager such as Azure Key Vault?
Answer determines whether Options A or C/D is viable. If the DB is classified as a non-secret store, Option A is acceptable. If not, Option C or B is required.
Q2. If client secrets must leave the DB, is a hybrid approach acceptable — where companymaster stores only a non-secret vault reference key (e.g. odgapiSecretRef = "odg-legacy-acme-corp-secret"), and the adapter fetches the actual secret from Azure Key Vault at runtime?
This is Option C. If "yes", Key Vault must be provisioned and managed by the infrastructure team. If "no" (must use a single generic credential), go to Option B.

Section 2 Usage Tracking Requirements

Q3. Who actively consumes the webserviceusage data today?
  • Is the admin PHP dashboard (Dashboard_model.php) used in production by internal staff, or only in development/staging?
  • Does the billing team or account management team query usage data for customer invoicing or reporting? If so, how and how frequently?
  • Are there any automated reports or scheduled jobs reading from webserviceusage?
If the dashboard is actively used and must be preserved, Options A/C (no adapter table) are simpler. Option D (log to Datadog) would require dashboard migration.
Q4. Is there a contractual or SLA obligation to provide per-customer API usage reports to legacy customers — for example, monthly usage summaries in a specific format? If so, what is the required frequency, format, and data granularity?
If per-customer reporting is contractual, Options B/C/D all need per-company attribution. Option B (shared credential) is only viable if the adapter's own table captures companyCode + webserviceCode on every call.
Q5. If a shared OAuth credential is adopted (Option B), is it acceptable to track per-customer usage only at the adapter level — via a new webserviceusage-equivalent table in the adapter database — rather than relying on ODG API logs?
The adapter DB is currently read-only SQLite. Adding a write path requires either enabling writes on SQLite or switching to Azure SQL / a separate audit database for production.

Section 3 Logging Scope & Data Sensitivity

Q6. The legacy PHP system logs only HTTP 200 successes. Should the adapter expand the logging scope to include failed requests? If so, which categories:
  • Auth failures (403 — invalid key, disabled account, not subscribed)
  • Upstream failures mapped to legacy errors
  • Validation errors (400)
  • No-result responses (404)
Logging failures is useful for debugging and detecting abuse, but increases write volume and may require storing HTTP status codes not in the legacy schema.
Q7. The legacy PHP system captures the clientId value that customers pass in their requests (via ?clientid= query param or <clientid> XML element). Should the adapter also capture this field?
  • Is clientId considered PII or sensitive under your data governance policy?
  • Are there compliance requirements (HIPAA, GDPR, etc.) that restrict storing this value?
The adapter currently passes clientid back to the customer in the response (legacy compatibility) but does not store it anywhere.
Q8. The legacy PHP system stores the full REQUEST_URI in queryData (e.g. /restws/bpguide?icd=724.2&bp=back&noi=strain). Is it acceptable to store the full request path + query string in the adapter's log/table, or must query parameters be sanitized or masked before storage?
Query strings may contain medical codes (ICD, NDC) that could be considered sensitive depending on your data classification policy.

Section 4 Infrastructure & Write Path

Q9. The adapter database is currently a read-only SQLite file. If adapter-level usage logging is required (Option B), what target database should be used in production?
  • SQLite with writes enabled (acceptable only for single-instance deployments)?
  • Azure SQL (same instance as the read tables, or separate)?
  • A separate audit/log database not shared with the companymaster validation tables?
If multiple adapter instances run behind a load balancer, SQLite is not viable as a shared write store. Azure SQL or an external log service is required.
Q10. If structured JSON logs emitted to stdout (→ Datadog or another log aggregator) are used instead of a DB table (Option D):
  • Can the PHP admin dashboard be retired when the PHP system is decommissioned?
  • Or does a replacement dashboard / report need to be built against the log platform?
  • Is there a Datadog workspace already provisioned for the adapter? (ODG Legacy API is already sending logs to Datadog — can usage events piggyback on the same pipeline?)

Section 5 Transition & Cutover

Q11. During the parallel-hostname phase (PHP and adapter both live), should both systems write to the same webserviceusage table — so usage data is consolidated in one place during the transition? Or should the adapter maintain a separate log, and the two be reconciled at cutover?
Writing from two apps to the same table requires the adapter to connect to the legacy MySQL database — currently not planned. Separate logs are simpler but need a merge strategy at cutover.
Q12. Is there a target cutover date or deadline by which the usage tracking design decision must be finalized before production traffic can be routed to the adapter? Are there billing or reporting cycles that dictate when the new system must be producing clean per-customer usage data?
If a billing cycle closes at month-end, the adapter must be logging correctly before the first day of that month to avoid gaps.

Additional Notes

  • The legacy PHP system never logs the X-ODG-KEY value to the webserviceusage table — only companyCode (resolved from the key) is stored. The adapter must follow the same rule: never persist the raw API key.
  • The adapter must also never log or persist OAuth bearer tokens, client IDs used as credentials, or client secrets — this is already enforced in src/upstream/odgClient.ts (token masked in debug logs) and must be maintained in any new logging code.
  • The WLD (Work Loss Data) exclusion from PHP logging was a one-off exception. Confirm whether this company is still an active customer before deciding whether to replicate it in the adapter.
  • The webservicemaster table (used by the PHP dashboard to JOIN service names) is unavailable in the adapter DB. If an adapter-level dashboard is needed, service names must come from the static service registry in src/config/serviceRegistry.ts.
  • This document covers only the design decision. No adapter source code changes have been made. Implementation will begin once the design questions above are resolved.
