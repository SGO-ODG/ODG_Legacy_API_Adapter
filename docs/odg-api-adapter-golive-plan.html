Strategic Decision: Should the ODG API Dev Team Take Full Ownership and Rewrite in .NET?

This is the most important decision in this document. The answer determines whether the current Node.js/Express implementation becomes the production system, or whether the ODG API Development team absorbs the project and rebuilds it in .NET — the same technology used across all ODGByMCG products.

Context

The Node.js/Express Legacy API Adapter was built as a temporary compatibility bridge to let legacy customers keep calling the old PHP API paths while the actual data is served by ODG API v1.2. The transformation logic (legacy XML in → ODG JSON → legacy XML/JSON out) is now approximately 90% complete and fully documented across all 5 in-scope APIs. The remaining work involves resolving ODG API data gaps, completing usage logging, and fixing a handful of edge cases.

At this point in the project it is worth asking: given that all the hard analytical and mapping work has been done, is it better to:

  1. Complete and ship the current Node.js adapter, maintaining it as a separate service with its own deployment pipeline and team dependency, or
  2. Hand the project to the ODG API Dev team to rewrite in .NET, eliminating the external Node.js dependency and consolidating ownership with the team that already maintains ODG API v1.2.

Pros & Cons Analysis

Option 1 — Complete the Node.js Adapter (current path) Option 2 — ODG API Dev Team Rewrites in .NET
PROS
  • ~90% of transformation logic is already implemented and tested — fastest path to go-live
  • All 5 in-scope routes (BPGuide, UR Advisor, OneSearch, Comorbidity, Reserve) are working
  • 3,000+ test cases already run and validated across 80+ customers
  • Authentication, OAuth token caching, and subscription validation all complete
  • Minimal rewrite risk — only edge-case fixes remain
  • Can go live in weeks, not months
 PROS
  • Same tech stack as all other ODGByMCG products (.NET) — no Node.js/Express expertise required for long-term maintenance
  • ODG API Dev team already owns the upstream v1.2 API — they best understand the response shapes and can fix both sides when data issues arise
  • All transformation logic, edge cases, and business rules are fully documented in the mapping spec and discrepancy reports — rewrite effort is primarily mechanical
  • Eliminates a cross-team dependency: one team owns both the upstream API and the compatibility bridge
  • No separate Node.js deployment pipeline, monitoring stack, or runtime to manage
  • Azure Key Vault integration, Azure SQL, Datadog — all already standard in the .NET deployment pipeline
  • When ODG API v1.2 is updated, the adapter can be updated in the same sprint by the same team
  • When legacy customers complete migration, retiring the adapter is a single team decision
  • Easier to pass security review — no unfamiliar open-source npm dependency chain
  • Claude Code can be used to accelerate the rewrite significantly — the SEAD team is already using it in active development. With all transformation logic fully documented and 3,000+ test cases to validate against, Claude Code can translate the Node.js implementation to .NET rapidly with high confidence. This substantially reduces the estimated rewrite timeline.
CONS
  • Requires ongoing Node.js/Express expertise for maintenance — a dependency on a different skill set from the rest of the ODGByMCG org
  • Separate deployment pipeline, container, and infrastructure to manage alongside .NET services
  • When ODG API v1.2 changes, two teams must coordinate to update the adapter
  • Security reviews of Node.js npm dependency chain add overhead
  • When legacy customers eventually migrate, adapter retirement requires coordinating with a different team
  • Long-term: maintaining a temporary Node.js service indefinitely is a growing maintenance burden
 CONS
  • Adds time before go-live — estimated 2–4 weeks to re-implement in .NET when using Claude Code (all logic is documented and test-validated; the translation is primarily mechanical). Without AI assistance, estimate 6–8 weeks.
  • Requires ODG API Dev team capacity allocation — must be planned against their existing backlog
  • Short-term knowledge transfer from the current Node.js implementation to the .NET team
  • All existing test cases must be re-run against the .NET implementation before go-live (test infrastructure already exists)
  • Risk of re-introducing bugs that the current implementation already solved (mitigated by the extensive test suite and Claude Code's ability to cross-reference the Node.js implementation)
Recommendation: Option 2 (ODG API Dev team takes ownership, .NET rewrite) is the better long-term decision — and the timeline concern is substantially reduced if the ODG API Dev team uses Claude Code during the rewrite, consistent with how the SEAD team is already using it. With all transformation logic fully documented and 3,000+ test cases to validate against, a Claude Code–assisted .NET rewrite is estimated at 2–4 weeks, bringing the total timeline impact to near parity with simply completing the Node.js adapter.

The resulting system will be more maintainable, owned by the team best positioned to maintain it, and consistent with the rest of the ODGByMCG platform stack. The SEAD team can remain available for questions during the rewrite sprint given their familiarity with the current implementation.

If business urgency still requires the absolute earliest possible go-live, complete the existing Node.js adapter now and schedule the .NET migration as a committed Phase 2 — but set a hard migration date before launch, not after.

This decision must be made in Week 1 as it determines all downstream planning, team capacity allocation, and timeline estimates.

Phase 1 — Decisions & Clarifications  ·  Target: Week 1–2

All items in Phase 1 are decision gates. No significant development work can begin on Phases 2–3 until these are answered. Run all of them in parallel — do not wait for one before asking another.

Step 1 — Strategic Platform Decision (Item #1)

Owner: Leadership / Product + ODG API Dev team lead

Convene a meeting between the adapter project stakeholder, ODG API Dev team lead, and Product leadership to decide:

  • Should the ODG API Dev team take ownership of this project and rebuild in .NET?
  • If yes: allocate team capacity and agree on a rewrite timeline. The existing Node.js implementation, mapping specifications, discrepancy reports, and test suites will be handed over as the design document. The SEAD team and the ODG API Dev team should plan to use Claude Code during the rewrite sprint — all transformation logic is fully documented and the 3,000+ test cases provide immediate validation feedback, making this an ideal AI-assisted development scenario. Estimated timeline with Claude Code: 2–4 weeks.
  • If no (complete Node.js adapter): commit to a maintenance plan — who owns the Node.js service, how is it deployed and monitored, and when is it retired?
All other phases below assume the Node.js adapter is being completed. If the .NET rewrite is chosen, the same phases apply — only the development owner and technology change. The phase structure, open items, and test validation steps are identical. Claude Code can be used in either path to accelerate the remaining development work.

Step 2 — ODG API Team: Data Gap Confirmations (Items #4–7)

Owner: ODG API Dev Team

Send the ODG API team the following specific codes and request confirmation within the week. The adapter team will provide the full request XML/URLs alongside this request.

  • UR Advisor — Does F40.231 (specific phobia, animal type) have guideline data in /tao/icds? If yes, raise a data gap ticket.
  • UR Advisor — In 3 CityofFortWorth multi-ICD requests, which specific code is unresolved by ODG v1.2? Is this a data gap?
  • BPGuide — Does M45.20 (ankylosing spondylitis, cervical) have guideline data in /guidelines? If yes, raise a data gap ticket.
  • Reserve Calculator — Do the NCCI/ICD combinations from DXCRM-TEST-3, DXCRM-TEST-9, CBCS-TEST-1 return results? If yes, raise a data coverage ticket for /calculator.

Step 3 — ODG API Team / Clinical: Actuarial Model Confirmation (Items #8–9)

Owner: ODG API Dev Team + Clinical / Product

Request written confirmation (email or Confluence comment) that the following ODG v1.2 values are authoritative and intentional — not a misconfiguration:

  • Adjusted duration days (5–15% difference vs. legacy) — Comorbidity and Reserve calculators
  • Risk assessment scores and status tiers (10–20 point differences causing Green/Yellow/Red tier changes)
  • Projected costs (10–30% difference across all cost bands) — Reserve calculator
  • PT visits range format (1-2 vs. legacy integer 1) — BPGuide
  • Clinical notes text (notes.medical / notes.indemnity) updated language — Reserve calculator

Also request any available change log, release notes, or model documentation that describes what changed. This will be the basis for customer communication in Phase 4.

Step 4 — Security / Architecture: Credential & Logging Design (Items #2–3)

Owner: Security / Architecture lead + Product owner

Answer the two usage logging blockers from the questionnaire:

  • Q1: Are per-company OAuth client secrets acceptable in the database (companymaster), or must they be stored in Azure Key Vault?
  • Q3: Who consumes webserviceusage data — billing team, admin dashboard, account management? Is per-customer attribution contractually required?

Based on the answers, confirm the design option:

  • Option A (secrets in DB, ODG API logs per-company attribution) — simplest, if policy allows
  • Option C (secrets in Azure Key Vault, ODG API logs per-company) — recommended if secrets must leave the DB
  • Option B (shared generic credential, adapter writes usage table) — only if Key Vault is not feasible
  • Option D (per-company credentials + structured Datadog logs) — if billing dashboard retirement is acceptable
Phase 2 — ODG API Data Fixes & Adapter Completion  ·  Target: Week 2–6

Development work runs in parallel with Phase 1 decisions. Adapter fixes (items #10–12) can begin immediately. Items dependent on Phase 1 answers start when confirmed.

Step 5 — Adapter Dev: ICD Input Sanitization (Item #10)

Owner: Adapter Dev Team — can start immediately

Add a shared ICD code sanitization routine applied in the BPGuide and UR Advisor request handlers before forwarding to ODG:

  • Strip trailing non-alphanumeric characters (dots, colons) from each ICD code — fixes CGU, NMMutual, Guidewire, Origami, Symetra trailing-dot/colon failures
  • Normalize 5-digit numeric codes without a decimal point to ICD-9 decimal format (e.g. 26615 → 266.15) — fixes 6 Symetra tests
  • Strip invalid extension suffixes from otherwise-numeric codes (e.g. 5522.32XA) — fixes 1 Symetra test

This single fix addresses 12 of 13 BPGuide HTTP status mismatches and 4 of 6 UR Advisor HTTP status mismatches.

Step 6 — Adapter Dev: Encova 400 Fix (Item #11)

Owner: Adapter Dev Team — can start immediately

Inspect the request XML for Encova-ODGWEBSVCS TEST-8 through TEST-13 to identify which field triggers the adapter's 400 rejection when legacy returned 200. Adjust the adapter's input validation or default handling to match legacy's permissive behavior for that input. Affects 6 tests (all go-live blockers for Encova).

Step 7 — Adapter Dev: Error Code Alignment (Item #12)

Owner: Adapter Dev Team

Review the Reserve Calculator request XML for tests where legacy returned 400 but the adapter returns 404 (cityofsanfrancisco ×5, GeorgiaDOAS ×3, LAWaterPower ×2). Determine whether these are validation failures (should return 400) or genuine no-data scenarios (404 is correct) and align adapter error handling accordingly.

Step 8 — ODG API Team: Resolve Data Gap Tickets (Items #4–7)

Owner: ODG API Dev Team — requires Phase 1 Step 2 confirmation first

For each confirmed data gap from Phase 1 Step 2, the ODG API team raises and resolves tickets to add the missing guideline or calculator coverage. The adapter team will re-run affected tests after each fix is deployed to staging.

Step 9 — Full Regression Test Run

After all Phase 2 adapter fixes are complete, re-run the full comparison test suite against the updated adapter. Expected outcomes:

  • BPGuide: 12 trailing-punctuation tests should now pass → target >97% pass rate
  • UR Advisor: 4 trailing-dot tests should now pass → target >99% pass rate
  • Reserve Calculator: 6 Encova tests should now pass; error code tests aligned
  • All APIs: re-confirm test baseline after ODG data gap fixes are deployed
Phase 3 — Infrastructure & Usage Logging  ·  Target: Week 4–8

Infrastructure work can begin in parallel with Phase 2 development once Phase 1 decisions are made. Allow 2–4 weeks for Azure provisioning.

Step 10 — Infrastructure: Azure Deployment Provisioning (Item #14)

Owner: Infrastructure / DevOps

Provision the production deployment environment:

  • Azure App Service or Container instance for the adapter (Node.js) or for hosting the .NET service (if rewrite chosen)
  • Azure SQL Database for companymaster and companywebservice tables (replaces local SQLite)
  • If Option C: Azure Key Vault — create, provision per-company secrets, assign Managed Identity to the adapter service
  • If Option B: Azure SQL writable instance for the usage logging table; design the webserviceusage-equivalent schema
  • Datadog agent/pipeline setup for adapter application logs (can share the existing ODG API Datadog workspace if available)
  • Application Insights or equivalent APM for the adapter

Step 11 — Adapter Dev: Usage Logging Implementation (Item #13)

Owner: Adapter Dev Team — requires Phase 1 Step 4 decisions on items #2 and #3

Implement the chosen usage logging design option:

  • Option C (recommended): Update src/db/companymaster.ts to resolve the vault reference key and fetch the actual secret from Azure Key Vault at token acquisition time. No usage table needed — ODG API logs provide per-customer attribution.
  • Option B: Add a write path to the adapter DB. Implement logUsage() equivalent: write companyCode, webserviceCode, queryData, clientHost, clientId, transactionTimestamp on every HTTP 200 response. Never log the raw X-ODG-KEY, OAuth tokens, or client secrets.
  • Option D: Emit a structured JSON log line to stdout on every HTTP 200 response. Include agreed schema fields. Verify Datadog pipeline ingests and indexes them correctly.
Regardless of option: replicate the legacy rule that company code WLD (Work Loss Data) is excluded from usage logging — unless confirmed that this company is no longer active.

Step 12 — Compliance / Legal: PII and Data Governance Sign-Off

Owner: Compliance / Legal

Before implementing usage logging, obtain sign-off on:

  • Q7: Is clientId (customer's own internal ID passed in requests) acceptable to store? Is it PII under HIPAA/GDPR?
  • Q8: Is the full REQUEST_URI / queryData acceptable to store? Medical codes (ICD, NDC, CPT) in query strings may be subject to data classification policy.
Phase 4 — Parallel Testing & Customer Communication  ·  Target: Week 6–10

Step 13 — Deploy Adapter to Staging with Production Data

Owner: Adapter Dev + Infrastructure

Deploy the adapter to the staging environment with:

  • Azure SQL populated with actual companymaster and companywebservice records
  • All per-company OAuth client credentials configured (Key Vault or DB per chosen option)
  • Datadog / APM monitoring active
  • A separate hostname from production PHP (e.g. legacy-adapter-staging.odgbymcg.com)

Step 14 — Customer Communication: Actuarial Model Changes (Item #15)

Owner: Product / Account Management — requires Phase 1 Step 3 written confirmation first

Using the written confirmation and change log obtained from the ODG API / Clinical team in Phase 1, prepare and send customer communications to all affected calculator customers. The communication should explain:

  • That the ODG API v1.2 uses an updated actuarial model with revised duration days, risk scores, and projected cost calculations
  • The expected magnitude of differences (5–15% on duration, 10–20 pts on risk scores, 10–30% on projected costs)
  • That these values represent the current, authoritative clinical data — not an error
  • What action (if any) customers need to take to recalibrate their workflows or benchmarks

Affected customers requiring communication: Caterpillar, CityofFortWorth, JohnsEastern, MissouriEmployersMut, PSWCA, WindhamGroup, Zenith, paradigm, Averitt, SheakleyUniservice, UnivofMichigan, CGU, Publix, Encova, SoCalGas, RMS, OhioBWC, Tysonfoods, and others with calculator content mismatches.

Step 15 — Parallel Hostname Testing (Item #16)

Owner: Adapter Dev + QA + each customer account team

Run both systems simultaneously under separate hostnames for a minimum 2-week window:

  • Legacy PHP: existing production hostname
  • Adapter: staging/parallel hostname

For each customer, replay a representative sample of recent real production requests against both endpoints and compare results. Pay particular attention to:

  • Calculator customers with actuarial model differences — ensure they have reviewed and accepted the new values
  • Any customer sending malformed ICD codes — confirm sanitization is working
  • Encova — verify the input validation fix resolves their 6 previously-failing tests
  • CityofFortWorth UR Advisor — verify data gap fix (if confirmed) or confirm customer accepts reduced rescount

Step 16 — Parity Sign-Off per Customer

Owner: Account Management + each customer

Obtain formal or documented sign-off from each legacy customer before their traffic is routed to the adapter. At minimum, each customer should confirm:

  • They have reviewed the actuarial model change communication (if applicable)
  • Their test systems are working correctly against the parallel adapter hostname
  • They have no outstanding issues before cutover
Phase 5 — Go-Live Cutover  ·  Target: Week 10–12

Step 17 — Pre-Cutover Checklist

Owner: All teams

Before routing any production traffic, verify:

  • All Phase 1 decisions documented and signed off
  • All Phase 2 adapter fixes in production build
  • All ODG data gap tickets resolved (or explicitly accepted as no-data for specific codes)
  • Usage logging operational and verified in staging
  • All customer parity sign-offs obtained
  • Datadog monitoring alerts configured (error rate, latency, 403/404 spikes)
  • Gateway route-back path verified — confirm the ability to instantly revert traffic to legacy PHP if a critical issue is found post-cutover
  • On-call rotation established for the first 2 weeks post-cutover

Step 18 — Staged Cutover (Item #17)

Owner: Infrastructure / DevOps + Adapter Dev

Route production traffic to the adapter in stages — do not cut all customers at once:

  1. Week 10: Route 1–2 low-risk, non-calculator customers first (e.g. UR Advisor-only customers with 100% pass rates: PMAGroup, SWIF, medata, MissouriEmployersMut)
  2. Week 11: Route remaining UR Advisor, BPGuide, and OneSearch customers
  3. Week 12: Route calculator customers after actuarial model communication is acknowledged

Monitor Datadog for 24–48 hours after each batch. Revert via gateway immediately if error rates spike or customers report issues.

Step 19 — Legacy PHP Retirement

Owner: Product + Infrastructure

Do not retire the legacy PHP system until:

  • All customers have been successfully routed to the adapter for at least 30 days
  • No customer has requested a route-back in that period
  • Usage logging in the adapter is confirmed to be capturing equivalent data to the PHP webserviceusage table
  • The PHP admin dashboard has been either migrated or formally decommissioned
