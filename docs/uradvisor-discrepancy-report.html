Discrepancy Type Reference

Each test case fires both the legacy PHP API and the adapter API in parallel, then compares HTTP status codes and the full parsed response body. Each output row is tagged with one of the following discrepancy types. All types except PASS cause the test to be reported as FAIL.

Type Counts as Failure? What It Means Detection Logic
PASS No HTTP status codes and full response bodies are identical on both sides. No differences found. Emitted when zero diff rows are produced for a test after all comparison checks complete.
HTTP_STATUS_DIFF Yes Legacy and adapter returned different HTTP status codes. Body comparison is skipped — the status difference is the entire result for that test. Triggered before body parsing when legacyResult.status !== adapterResult.status.
CONTENT_MISMATCH Yes A specific field value differs between legacy and adapter. Array records are matched by code key (ICD code, CPT code, etc.); records unique to one side are silently skipped — only key-matched records are compared. Recursive comparator walks both parsed objects. Any leaf-value difference produces this type.
EMPTY_VS_RESULTS Yes One side returned a non-empty array for a matched section and the other returned an empty array. More severe than a simple count difference — one side has data and the other has none. Triggered when legacy.length > 0 && adapter.length === 0 or vice versa for a matched response section.
FORMAT_MISMATCH Yes Legacy responded with one format (XML or JSON) but the adapter responded with the other. Triggered when detectFormat(legacy) !== detectFormat(adapter) after both HTTP calls succeed with the same status code.
PARSE_ERROR Yes One or both responses could not be parsed as valid XML or JSON. Body comparison is skipped and the parse exception message is recorded in the detail column. Triggered when JSON.parse() or XMLParser.parse() throws for either side's response body.
NETWORK_ERROR Yes The HTTP request to the legacy or adapter host failed at the network level (connection refused, DNS failure, timeout, etc.). No HTTP status code or response body is available. Triggered when axios.get() itself throws — a network-level failure, distinct from an HTTP error response.

Item 1 — AU Content Gap: ICD-10 codes C49.21 and C49.22  PENDING SEAD

ICD-10 codes C49.21 (Malignant neoplasm of connective and soft tissue of right upper limb) and C49.22 (left upper limb) exist in the legacy UR Advisor AU dataset — the legacy PHP API returns HTTP 200 with valid AU results for both. The adapter calls the ODG v1.2 API with country/AU and receives no data, returning HTTP 404 to the customer.

Root cause: These ICD-10 codes appear to be present in the legacy content database for the AU jurisdiction but have not been published to the ODG v1.2 AU dataset. This is a content publishing gap — not an adapter code defect. The adapter correctly relays the ODG API response.

Action required — SEAD team: Verify whether C49.21 and C49.22 are intentionally excluded from the AU ODG v1.2 dataset or missing due to a publishing oversight. If this content should be present, the SEAD team needs to publish it to the ODG API before the adapter can return results for these codes.

Item 2 — Legacy Drop-Digit Fallback for Unrecognised ICD Codes  PRODUCT ACCEPTED

ICD code S022XX submitted by ReviewWorks contains uppercase X placeholder characters. The legacy PHP API silently truncates or normalises such codes to a valid base code before the upstream lookup and returns HTTP 200. The adapter passes the submitted code as-is to ODG v1.2, which does not recognise it and returns HTTP 404.

Product decision — confirmed, no adapter fix: This is a legacy-only drop-digit normalisation behavior. Product has reviewed and confirmed that the adapter should not auto-correct or apply a drop-digit fallback for unrecognised ICD codes. Silently normalising a submitted code risks returning guidelines for a different code than the one the caller intended, which could cause clinical confusion. This decision is consistent with the same resolution already documented in the Best Practice Guide and One Search discrepancy reports.

The 404 response from the adapter for S022XX is therefore correct and expected behavior. The affected customer (ReviewWorks) should be advised to submit well-formed ICD-10 codes without placeholder X characters. No code change is required in the adapter.
