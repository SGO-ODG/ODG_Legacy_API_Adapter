Scenario 1 — Successful Request (Happy Path)

A legacy customer sends a valid request with a known, active X-ODG-KEY. Subscription is current. The adapter validates auth, calls ODG API, transforms the response, returns the legacy-format reply, and writes a usage log row asynchronously.

The token cache branch shows both paths: HIT (token already cached and valid) and MISS (first request, or token expired).

Scenario 2 — Authentication Failure

The adapter enforces the full legacy auth contract before making any upstream call. Validation runs in order: key lookup → disabled check → service registry → subscription lookup → date range. The first failing check returns the exact legacy error body — no ODG API call is ever made.

Key design rule: All auth validation runs before any attempt to fetch a Bearer token or call ODG API. OAuth credentials and upstream URLs are never exposed to the customer in any error response.

Scenario 3 — Upstream 401: Token Invalidation and Single Retry

If ODG API returns 401 Unauthorized (e.g. token expired mid-flight between the cache skew check and the actual call), the adapter invalidates the cached token, fetches one fresh token, and retries the original request exactly once. If the retry also fails, the adapter maps the error to a safe legacy error response — the customer never sees a raw upstream 401 or any OAuth detail.

Single-flight token refresh: If two requests arrive simultaneously when the token is expired, only one network call to the OAuth server is made. All concurrent requests share one in-flight promise, preventing a "token thundering herd" on cache miss.

Scenario 4 — Endpoint-Specific ODG API Targets

After auth and token resolution (steps 1–6 of Scenario 1), each endpoint calls a different ODG v1.2 path. The table below shows what step 7 looks like per endpoint.
