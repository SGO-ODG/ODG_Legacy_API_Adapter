Discrepancy Type Reference

Each test case fires both the legacy PHP API and the adapter in parallel. The compare script tags each output row with one of the types below. EXPECTED_DIFF and WITHIN_THRESHOLD do not count as failures and are excluded from the failure count; a test fails only when CONTENT_MISMATCH, HTTP_STATUS_DIFF, NETWORK_ERROR, FORMAT_MISMATCH, PARSE_ERROR, or EMPTY_VS_RESULTS appears in any of its rows.

Item 1 — cfactors.trigger returns ICD-10 identifier in adapter; legacy returned ICD-9 (12 tests)  PENDING PRODUCT CONFIRMATION

The cfactors section reports which comorbidity factor triggered and what code activated it. Legacy returned the ICD-9 code that the customer submitted (e.g. 401 for hypertension, 250 for diabetes, 278 for obesity). The adapter returns the ICD-10 equivalent code that ODG v1.2 uses internally (e.g. I10, E10, E65). This affects hypertension, diabetes, obesity, depression, and smoker factors across 5 customers.

Open question for Product: The trigger field in cfactors was previously the customer-submitted ICD-9 code. It will now be an ODG v1.2 ICD-10 code. Customers who display this field in their UIs will see a code format change. Please confirm this is acceptable before cutover, or specify whether the adapter should map the trigger back to the customer-submitted input code.

Item 2 — Adapter returns complete ICD code list; legacy truncated at index 13 (Zenith, 41 tests)  PRODUCT ACCEPTED

For many Zenith test cases, the icdcodes array in the legacy response ends at index 12 — entries at positions 13 and above are returned as empty strings. The adapter returns ICD code objects for all positions the ODG v1.2 API provides, resulting in populated objects at positions 13–16+ where the legacy response had empty values.

Product decision: Adapter behavior is correct and an improvement. The legacy PHP had a code-side truncation or data gap at that array position. The adapter returns the complete set of ICD codes as provided by ODG v1.2.

Item 3 — alertdesc.yellow populated in adapter where legacy returned empty string (11 tests)  PRODUCT ACCEPTED  Adapter Fix Applied

For certain yellow-alert risk cases, the legacy PHP response returned an alertdesc object with an empty yellow value. The adapter returns the actual alert description text from ODG v1.2: "Consider early intervention and priority medical case management." This is distinct from the EXPECTED_DIFF category (cases where legacy had the alert text and the adapter currently omits the field); here, the direction is reversed — the adapter has the text and legacy was returning empty.

Product decision: Adapter behavior is correct and an improvement. Returning the alert description text is better than returning an empty string. No change to the adapter is required. Note that alertdesc is not yet fully implemented in all adapter code paths — the EXPECTED_DIFF rows elsewhere in this report reflect cases where legacy populated the alert and the adapter still omits it.
Fix applied — adapter codebase: alertdesc colour children are now gated on the presence of a matching alert value in the mapped cfactors output. A colour (e.g. yellow) is only emitted in alertdesc if at least one applied cfactor carries alert: "yellow". Orphaned descriptions with no corresponding cfactor alert are suppressed. Fix is in src/transformers/calculator.ts — pending re-run of comparison tests to confirm.

Item 4 — Systematic comorbidity calculation differences between ODG v1.2 and legacy (~240 tests, 14 customers)  PENDING PRODUCT CONFIRMATION

The most widespread finding is a systematic divergence in the comorbidity calculator's output between the legacy PHP/ODG system and ODG v1.2. The difference manifests consistently across the following fields:

  • riskassessment.magnitude and riskassessment.volatility (132 and 128 failing tests respectively): these are the spread components of the risk score. Even when riskassessment.score is within the ±5 threshold, magnitude and volatility frequently differ beyond ±5. The root cause appears to be a change in the ODG v1.2 actuarial model for these sub-components.
  • riskassessment.score (20 tests directly flagged as CONTENT_MISMATCH): cases where the score itself exceeds the ±5 threshold, most severely in JohnsEastern-TEST-19 (legacy: 46.83 → adapter: 72.76) and TEST-22 (legacy: 77.17 → adapter: 82.12).
  • riskassessment.status (26 tests): a consequence of score boundary crossings. The status label (Green/Yellow/Orange/Red) flips when the score shifts across a band threshold. Examples: "Green (Moderate)" → "Yellow (Cautionary)", "Yellow (Cautionary)" → "Orange (High)".
  • adjustedduration.cp95.days and adjustedduration.cp100.days (116 and 107 failing tests): adjusted return-to-work duration predictions at the 95th and 100th percentile differ outside the ±5 day threshold.
  • adjustedduration.bp.days (27 failing tests): best-practice duration differs, most notably for PSWCA (9 tests) and JohnsEastern.
  • adjustedsummaryguidelines.* (atriskclaims, midrangeclaims, atriskallabsence, midrangeallabsence — 51/46/45/35 failing tests): population-level statistics for the matched diagnosis group differ outside tolerance.
Open question for Product: The ODG v1.2 comorbidity calculator systematically produces different outputs from the legacy system for magnitude, volatility, duration, and population statistics. The most likely explanation is an intentional update to the actuarial model in ODG v1.2. Before cutover, Product must confirm:
  1. Is the ODG v1.2 comorbidity model intentionally different from the legacy model? If yes, the adapter results are correct and customers should expect updated numbers.
  2. Is the visible riskassessment.status band label change (e.g. Yellow → Orange) acceptable to affected customers? This is the most customer-visible impact — 26 test cases cross a band boundary.
  3. Are the extreme outliers (JohnsEastern TEST-19: duration 27 days → 118 days; TEST-22: 142 days → 198 days) expected model outputs for those specific input combinations, or do they indicate a potential input mapping issue?

Item 5 — adjustedsummaryguidelines.midrangeallabsence = 0 in legacy vs non-zero in adapter (Caterpillar, 3 tests)  PENDING PRODUCT DECISION

Three Caterpillar test cases return adjustedsummaryguidelines.midrangeallabsence = 0 in the legacy response but non-zero values in the adapter. For the same inputs, the adapter returns 101, 53, and 75 respectively. A value of 0 is anomalous for this population-level statistic field and suggests either a data gap in the legacy ODG dataset for those specific diagnosis groups, or a PHP logic fault. The adapter, drawing from ODG v1.2, returns the statistically expected non-zero population value.

Open question for Product/SEAD: Please confirm whether the legacy value of 0 for midrangeallabsence in these cases was intentional (e.g., a specific data suppression rule) or a known legacy data gap/bug. If the legacy value of 0 was a bug, the adapter result is correct. If 0 was intentional, SEAD should verify whether ODG v1.2 applies the same suppression rule.
