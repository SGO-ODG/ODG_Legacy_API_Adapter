Finding 1 — ODG API Data Gaps: Valid Codes Returning No Results Critical

The following specific ICD-10 and NCCI codes were successfully resolved by the legacy PHP database (returning HTTP 200 with guideline data) but return no results in ODG v1.2 (HTTP 404). These are not malformed inputs — they are standard or valid code formats. The adapter cannot compensate for missing upstream data.

Impact: Customers who submit these codes via the adapter will receive a 404 "no results" response instead of the guideline data they received from the legacy system. This is a live regression for those customers.

Finding 2 — Alert Color & AlertDesc Fields Not Available in ODG v1.2 Response Critical

The legacy calculator APIs returned two types of severity indicator fields inside the adjusted duration response that are currently missing from the adapter:

  1. alert — a color string (yellow, red, green) nested inside each adjustedduration.bp, adjustedduration.cp95, and adjustedduration.cp100 object
  2. alertdesc — a keyed object where the key is the alert color and the value is a descriptive text string, e.g. <alertdesc><yellow>Consider early intervention...</yellow></alertdesc>
Root cause: The ODG v1.2 /calculator response either does not include this alert data, or it is present under a field path that has not been identified and documented. The adapter team has not been able to locate the source field for alert color or alert description in the v1.2 API response. Until the source field is confirmed by the ODG API team, the adapter cannot implement this mapping.

Finding 3 — Actuarial Model Version Changes: Duration, Risk Scores & Projected Costs Differ Systematically High Priority

Across all calculator and guideline API tests, the most widespread category of differences involves calculated numeric values that differ systematically between legacy and ODG v1.2. These are not bugs in the adapter's data mapping — the adapter faithfully transmits ODG v1.2 values. The differences reflect an updated actuarial model in v1.2 compared to the legacy database.

Why this is a go-live risk: Legacy customers have calibrated their claim management workflows, internal benchmarks, and SLA thresholds around the legacy numeric values. Without advance notice and ODG's written confirmation that v1.2 values are authoritative, customers may perceive the new values as system errors and reject the migration.

Finding 4 — Clinical Notes Text Changes in Reserve Calculator Medium

The notes.medical and notes.indemnity fields in the reserve calculator response contain clinical narrative text. In approximately 17 tests, the text returned by the adapter (sourced from ODG v1.2) differs from the legacy text.

FieldAffected TestsPattern
notes.medical ~17 tests Clinical narrative text differs — ODG v1.2 appears to use updated or revised clinical notes language compared to the legacy database text.
notes.indemnity sub-fields ~3–4 tests Same pattern — indemnity notes text differs.
Why this matters: Some customers parse or display these notes fields in their claim management systems or reports. If the text has materially changed, customers may need to update their downstream handling.
Questions for ODG API team / Product:
  1. Confirm whether the clinical notes text returned by ODG v1.2 /calculator is the current authoritative text — i.e., intentionally revised since the legacy database was last updated.
  2. If yes, provide a summary of what changed (e.g., "updated medical duration rationale language") so customers can be notified.
  3. If this was an unintentional change, identify the correct field or parameter to use to retrieve the same notes text as the legacy system.
